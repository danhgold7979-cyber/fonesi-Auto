## 2. Closed catalog and private selection

Keep the current canonical candidate schema unchanged:
`{schema:1,release,archive:{url,bytes,sha256},files:[{path,bytes,sha256,peMachine,peMagic}]}`.
Existing37.0.1 canonical bytes, archive/manifest hashes and historical ledger references remain unchanged. Introduce a separate immutable module-local catalog envelope:
`{version:1,installTargetArchiveSha256,entries:[{candidate,activationAllowed,launchAllowed,versionObservation:{protocol:'1.0.41',release,buildGrammar:'DECIMAL_1_20'}}]}`.

- Entries are deeply frozen, exact keys, one to four, sorted by archive digest; archive digests, manifest digests and release identifiers are unique. `installTargetArchiveSha256` identifies exactly one entry.
- Each candidate has exactly the reviewed14 flat filenames and one `platform-tools/` ZIP directory in this bounded slice. Inventory changes beyond that closed shape require review rather than a parser fallback. PE facts are per-file exact values, not inferred from hostx64. Non-PE fields are both null. Expanded byte total is the safe exact sum of file rows; archive bytes and each file bytes are exact candidate facts within unchanged global128MiB custody budget.
- `versionObservation.release` exactly equals candidate.release; buildGrammar is the sole literal DECIMAL_1_20, preserving the reviewed bounded decimal build suffix rather than inventing a build number. The native result must match the selected exact release, protocol and existing full output grammar; no arbitrary regex is accepted. No new exact-build claim is introduced.
- `activationAllowed` and `launchAllowed` are exact build-owned booleans. Install target requires both true. The flags are independent: activationAllowed=false blocks a new INSTALL/ROLLBACK selection, but an already selected active entry with launchAllowed=true remains launchable. launchAllowed=false blocks execution of an already selected runtime. Known metadata for retained history stays in the finite catalog even when these become false. These policy facts are not license or recipient grants.
- Main private `resolveAcceptedCandidate(archiveSha256)` returns a catalog-owned immutable record or null. An internal identity check rejects copied/manufactured record objects where a candidate handle is required. No public factory option, environment flag, renderer argument or filesystem JSON imports an arbitrary catalog.
- INSTALL always selects the build's fixed install target. ROLLBACK always selects the latest settled `previousActiveSha256`, requires nonnull and distinct from `activeSha256`, and resolves it in the current catalog with activationAllowed=true and launchAllowed=true. No UI picks a digest. A known but activation-revoked candidate cannot be selected for rollback; a launch-revoked candidate cannot execute. Its old metadata remains usable to validate history and retained physical bytes; activation revocation alone does not revoke launch eligibility of an already selected active runtime.
- Additions must retain every historical digest needed to interpret a managed root's chain, within the existing four-entry bound. Unknown historical candidate records fail closed. Revocation changes eligibility, not known metadata; an old revoked predecessor does not invalidate an otherwise valid newer active chain. An intact settled active candidate with launchAllowed=false reports the distinct private POLICY_DENIED status described below; it cannot execute but permits a separately confirmed INSTALL of the allowed fixed target. This is not an uncertain chain. Capacity exhaustion refuses rather than dropping history or pruning.

Tests may substitute a complete two-entry static catalog at the existing module-transformation boundary, with explicit synthetic labels. No test switch or candidate dependency injection enters production constructors.

## 4. Main-owned interaction and exact transition

Use the existing Help setup action and existing main-native issuer; add a native operation choice only when a fully inspected distinct prior candidate is available. Do not add a renderer rollback target, route, URL or digest argument. Main snapshots current ledger revision, current digest, prior digest and catalog identity under the existing exclusive SETUP custody token before presenting the choice. Any unavailable prior is explained as unavailable, not replaced by another version found on disk/PATH.

Native choice contains Cancel(default/cancel index0), Install fixed target, and Restore retained previous only when admitted. Before issuing a rollback grant, a second Cancel-default confirmation states the exact main-owned current/prior release, no download, retained newer bytes, byte-verification versus execution distinction, and no server/device action. Recipient terms/entity statement is still genuine and explicit; retained bytes or an old receipt do not synthesize consent. Local/download INSTALL presentation retains its existing genuine terms and final confirmation. Cancel/decline writes no provisioning intent or payload.

Private native result discriminant:
- INSTALL: `{ok:true,kind:'INSTALL',route:'LOCAL_ARCHIVE'|'OFFICIAL_DOWNLOAD',archivePath:string|null}`.
- ROLLBACK: `{ok:true,kind:'ROLLBACK',route:'RETAINED_RUNTIME',archivePath:null}`.
- refusal: exact `{ok:false,code:'TERMS_DECLINED'|'TERMS_REQUIRED'|'SETUP_CANCELLED',action:null|'INSTALL'|'ROLLBACK'}`. action is null only before a native action choice; once chosen it is retained on final-confirmation Cancel/decline and subsequent refusal. Main retains the same selected-action fact across exceptions/revocation; it never guesses it from a failed return.

The per-process WeakMap grant additionally binds kind, selected catalog identity, expected ledger revision, current/prior digests and captured owner/session generation. None is caller-supplied authority. Every native await, audit await and final callback rechecks owner/session/SETUP token and the exact captured chain/CAS. Revocation invalidates the grant without granting cleanup authority. Concurrent native READ/VERSION or unresolved helper/read holder returns BUSY before dialog/effect; queued grants are not created.

ROLLBACK sequence:
1. Reserve SETUP synchronously before callbacks; verify owner/location, complete settled chain, current catalog and all global budgets. Fully verify both current and selected prior runtimes. Missing, tampered, no-longer-accepted or non-distinct prior refuses before intent. Inspecting a directory never adopts it.
2. Complete genuine confirmation and flush the operation's audit INTENT. Recheck captured process revision and durable installation revision; revalidate both runtimes and chain before exclusive ledger intent creation. Selection comes only from that chain's previous digest.
3. Append new v1 ROLLBACK/RETAINED_RUNTIME intent with prior candidate manifest/archive hashes. Do not read/download/extract an archive; do not copy, delete or overwrite either runtime.
4. Revalidate full current/prior files, complete inventory, pending-token/chain, owner/session/SETUP fences immediately before settlement. Append/sync/close/readback ACTIVATED selecting prior; settlement.previousActiveSha256 becomes the former current. A later rollback may toggle only to this newly recorded predecessor after fresh confirmation/CAS/full verification.
5. Only confirmed settlement plus final ownership may report VERIFIED_LOCAL. Increment durable installation revision; retain both directories and all records. Flush RESULT; logging failure degrades health but cannot turn a known activation into NOT_ACTIVATED or retry it.

INSTALL A→B uses the same shared scan and final verification of retained currentA and newly publishedB. Installing already-active target is idempotent after full verification, with unchanged revision/no new intent. Installing B when a complete validB directory already exists may reuse only after full verification; no merge/overwrite. The source two-entry test starts with a build whose fixed targetA, then reopens under the next synthetic build catalog[A,B] with fixed targetB, rather than granting callers arbitrary installation selection.

## 5. Failure, observation and shutdown

No new free-text errors.

An uncertain intent/settlement, changed ownership, partial publication, unknown participant or post-intent failed physical admission is OUTCOME_UNKNOWN with preserved records/bytes and retained operation/custody. Known safely retired pre-publication INSTALL fetch/archive failure may retain the existing exact NOT_ACTIVATED policy; do not generalize it to mutation uncertainty.
