## 1. Scope and existing gap

Canonical [Phase2 P2-02/P2-03](PHASE-02-adb-device-fleet.md) requires owned server lifecycle and timestamped, generation-fenced discovery with preserved identities/history. Existing main initializes RegistryStore/STARTUP and CaptureStore recovery but never calls discovery ingestion; fleet availability is hardcoded BINARY_UNAVAILABLE. The reviewed [private server](P2-RETAINED-SERVER-INTEGRATION-CONTRACT.md), [ingestion](P2-DISCOVERY-INGESTION-CONTRACT.md), and [owned acquisition](P2-OWNED-DISCOVERY-ACQUISITION-CONTRACT.md) supply these missing effects without a public route.

This slice composes those implementations into actual main/preload/Help with four explicit methods: status Read, Start, Refresh, Stop. No automatic Start, scan, timer, reconnect, polling or retry. No device command, input/capture execution, wireless operation, identity resolver, serial disclosure, synthetic production provider or arbitrary executable/URL/path. Existing startup preference/fleet reads remain read-only. With no subscription/polling, the renderer cannot instantly know idle native loss: displayed observations are captured-time. Main synchronously denies future projections/effects on known loss; renderer clears cached state on the next observed lifecycle/error/revocation result. Navigation/window loss already invalidates the UI/session. No new watcher or notification channel is implied. Current KnownFolder/profile-absence, supported path, owned launch/context, catalog/runtime/custody, private endpoint and owner guards remain unchanged; denial is displayed, never bypassed with profile/environment/account changes.

## 2. Lifetime choice: one attempt per application launch

RegistryStore.startup() already refuses after runtime exists; it increments durable host_epoch, retires old bindings and reconstructs disconnected history only at genuine application startup. Ingestion requires a fresh disconnected registry with sequence null. There is no adopted in-process epoch-reset API.

Therefore one accepted START reservation consumes the launch's single server attempt, even if its audit/native work later fails. Before reservation, invalid request/CAS/context/installation or unavailable audit may refuse without consuming the attempt. Never call startup twice, reconstruct an empty registry, offset/reset sequence, create a replacement ingestion owner, or discard historical devices to enable restart. STOP before any START is a cleanup no-op and does not consume the attempt. Once a START was accepted, stopped/failed/uncertain sessions cannot start again in this process: fixed RESTART_REQUIRED. Genuine application relaunch performs the existing durable STARTUP path. This is a bounded initial implementation, not a claim that P2 reconnect/restart criteria are complete.

Main constructs one facade, shares the actual setup/version runtime custody, and creates the private SERVER_ONLY controller only for accepted START with its captured installation revision and ViewSession generation. After successful START and final retained-token admission, obtain the actual server-service-branded provider and construct ingestion once against the existing RegistryStore and actual durable revision reader. No same-name standalone CJS imports or mixed module instances: main's ordinary source graph composes factory, server service and ingestion in one bundle, preserving private WeakMaps. Injected factories cannot mint native provider provenance.

## 3. Exact public wire

New private channel `auto:discovery:v1`, frozen `window.discovery` wrappers `get()`, `start(expectedRevision, expectedInstallationRevision)`, `refresh(expectedRevision)`, `stop()`. No subscriptions or exposed event listeners. All request objects exact, duplicate-aware JSON, UTF8 <=16384 bytes; scalar revisions safe nonnegative integers (installation positive), requestId existing canonical p1… safe integer convention. Extra fields/getters/non-plain objects rejected before effect.

Requests:
- `{version:1,requestId,method:'discovery.get'}`
- `{version:1,requestId,method:'discovery.start',expectedRevision,expectedInstallationRevision}`
- `{version:1,requestId,method:'discovery.refresh',expectedRevision}`
- `{version:1,requestId,method:'discovery.stop'}`

Success exact `{version:1,requestId,ok:true,outcome:'OBSERVED'|'PENDING',snapshot,diagnosticId,loggingHealth}`. GET alone returns OBSERVED (a status observation, not native operation success); effect methods return PENDING after reservation. Error exact `{version:1,requestId,ok:false,outcome:'NOT_STARTED'|'OUTCOME_UNKNOWN',code,diagnosticId,loggingHealth}`. requestId may be null only on uncorrelatable parse/local failure. diagnosticId canonical UUID or null; null always DEGRADED. No inferred main origin from a diagnostic ID. Local timeout is OUTCOME_UNKNOWN, never cancellation. Installation/native outcome never inferred from an IPC acknowledgment.

Snapshot exact fields:
`{revision,installationRevision,state,operationId,operation,lastOutcome,code,registryRevision,observedAtUtc,restartRequired}`.
- revision: process-local interaction CAS, monotonically increased on each accepted operation reservation and terminal transition; fail before effect on overflow. Separate from registry/durable revisions.
- installationRevision: captured positive installed revision or null, not a grant. Before any server attempt, idle GET and START use the existing `runtimeCustody.acquireRead()` exact READ_VERIFIED_ONLY observation, `assertRead(token)` with ordinary final fences, and `releaseRead(token)`. Capture the observation while held; only deliver after actual RETIRED release, with no assertion that bytes remain continuously current afterward. START's factory independently rechecks the same expected installation revision on its own actual retained holder before executable handoff. Busy setup/version custody refuses, no fallback. GET after a server is constructed never acquires a competing holder or revalidates native health: it returns captured status, guarded by the existing callback-free epoch witness; a known invalid witness revokes projection and initiates cleanup. Release uncertainty latches unknown and retains actual promise/token, not an idle/read success. If GET has no operationId, return fixed OUTCOME_UNKNOWN error (diagnostic if allocated, otherwise null/DEGRADED) and an internal cleanup-required latch; do not manufacture an operation snapshot or misuse the allocation-exhausted tuple. Future GET remains a fixed unknown error until actual cleanup settles; ordinary Start/Refresh refuse.
- state: UNAVAILABLE | IDLE | STARTING | READY | REFRESHING | STOPPING | STOPPED | FAILED | OUTCOME_UNKNOWN.
- operation: null | START | REFRESH | STOP; operationId null or canonical UUID. Pending states require matching operation and ID. Terminal retains last operation/ID for explicit correlation; initial IDLE/UNAVAILABLE have both null.
- lastOutcome: NONE | PENDING | STARTED | COMMITTED | NOT_COMMITTED | FAILED | CLEANUP_RETIRED | UNRETIRED. Initial NONE; pending PENDING; READY after START requires STARTED; READY after accepted refresh requires COMMITTED or NOT_COMMITTED. STOPPED requires CLEANUP_RETIRED. Unknown requires UNRETIRED; known COMMITTED with invalid projection uses the FAILED/COMMITTED tuple below, never unknown DB outcome. Cleanup retirement is never a fabricated ordinary observed STOP.
- code: null for initial IDLE, PENDING, STARTED, current COMMITTED and CLEANUP_RETIRED; otherwise exact fixed code. A known durable COMMITTED with stale projection preserves COMMITTED and reports SESSION_REVOKED/OWNER_REVOKED/CLOSED as applicable, never NOT_COMMITTED.
- registryRevision: actual durable ledger revision or null when unavailable, not an invented process registry revision. observedAtUtc: null except the last successfully admitted discovery observation; becomes null whenever live projection invalidated. No implication of continuous monitoring.
- restartRequired: false before an accepted START, true after that session becomes stopped/failed/revoked/uncertain; false during its valid READY/pending work. No UI restart command added.

In the tuple table, “fixed failure” is one of STALE_REVISION, SESSION_REVOKED, OWNER_REVOKED, AUDIT_UNAVAILABLE, DISCOVERY_FAILED, DEADLINE, REVISION_EXHAUSTED, LIMIT_EXCEEDED, RECOVERY_REQUIRED, INTERNAL_FAILURE, CLOSED; transport ambiguity instead uses OUTCOME_UNKNOWN.

Fixed codes: INVALID_TRANSPORT, PAYLOAD_TOO_LARGE, INVALID_JSON, INVALID_SHAPE, UNSUPPORTED_VERSION, UNKNOWN_METHOD, UNTRUSTED_SENDER, SESSION_UNAVAILABLE, SESSION_REVOKED, OWNER_REVOKED, BUSY, STALE_REVISION, STALE_INSTALLATION, NOT_PROVISIONED, POLICY_DENIED, RETAINED_HOST_DISABLED, UNSUPPORTED_PATH, AUDIT_UNAVAILABLE, RESTART_REQUIRED, DISCOVERY_FAILED, DEADLINE, REVISION_EXHAUSTED, LIMIT_EXCEEDED, RECOVERY_REQUIRED, INTERNAL_FAILURE, TIMEOUT, TRANSPORT_FAILED, OUTCOME_UNKNOWN, CLOSED. Internal host/durable codes are mapped by literal table, never exception.message. Unknown native result after handoff is OUTCOME_UNKNOWN; a settled known failed query is DISCOVERY_FAILED. Durable COMMITTED/NOT_COMMITTED/OUTCOME_UNKNOWN distinctions must survive mapping.

### Normative state tuples and allocation

All snapshots obey the following combinations; other combinations reject. `I` is positive installation revision, `O` the matching nonnull operation UUID, `R` the actual known durable revision or null, and `T` the safe observation timestamp from a current committed refresh only. Pending/terminal operation IDs never become authority.

| State | operation / ID | lastOutcome | code | installation / observed time / restartRequired |
|---|---|---|---|---|
| IDLE | null / null | NONE | null | I / null / false |
| UNAVAILABLE | null / null | NONE | NOT_PROVISIONED/POLICY_DENIED/RETAINED_HOST_DISABLED/UNSUPPORTED_PATH/OWNER_REVOKED/RECOVERY_REQUIRED/CLOSED | I or null / null / false |
| STARTING | START / O | PENDING | null | I / null / false |
| READY after Start | START / O | STARTED | null | I / null / false |
| REFRESHING | REFRESH / O | PENDING | null | I / null / false |
| READY after Refresh | REFRESH / O | COMMITTED | null | I / T / false |
| READY after pre-commit refusal with valid epoch | REFRESH / O | NOT_COMMITTED | fixed failure | I / null / false |
| FAILED after known failed Start | START / O | FAILED | fixed failure | I / null / true |
| FAILED after known failed Refresh and lost epoch | REFRESH / O | NOT_COMMITTED | fixed failure | I / null / true |
| FAILED after known committed Refresh but lost publication authority | REFRESH / O | COMMITTED | SESSION_REVOKED/OWNER_REVOKED/CLOSED | I / null / true |
| STOPPING | STOP / O | PENDING | null | I or null / null / attempt already consumed |
| STOPPED | STOP / O | CLEANUP_RETIRED | null | I or null / null / attempt already consumed |
| OUTCOME_UNKNOWN | START/REFRESH/STOP / O | UNRETIRED | OUTCOME_UNKNOWN/RECOVERY_REQUIRED | I or null / null / true |
| OUTCOME_UNKNOWN allocation-exhausted cleanup | null / null | UNRETIRED | INTERNAL_FAILURE/REVISION_EXHAUSTED/LIMIT_EXCEEDED | I or null / null / attempt already consumed |

A durable OUTCOME_UNKNOWN refresh maps unknown state; a known COMMITTED receipt cannot be overwritten by a later cleanup outcome: retain its operation receipt privately and preserve lastOutcome COMMITTED in the stale-publication FAILED tuple before any explicit Stop transition. Cleanup state then refers to the new STOP operation, not retroactive mutation of the refresh receipt. GET failure returns an error without inventing a successful snapshot or rewriting pending state. Initial/pre-start explicit Stop may reserve its own O and transition STOPPING→STOPPED/CLEANUP_RETIRED with restartRequired false; a subsequent Start is still permitted if no START reservation has ever been accepted. This cleanup no-op performs no factory construction. Its completed receipt is a separate no-resource latch, not the actual attempt cleanup latch: START refuses BUSY until the no-resource Stop and its audit work have actually settled, then atomically discards only that provably settled/no-resource latch while reserving the first START and fresh operation generation. The subsequent real attempt has its own retained cleanup promise; a later Stop must not reuse the old no-resource result. Never replace a pending, uncertain or resource-bearing cleanup latch. Repeated completed Stop returns PENDING acknowledgment of the same already-retired cleanup operation/status (no duplicate reservation/audit), reconciled by explicit GET.

Capture all callbacks once. Unique UUID allocation across facade operation/diagnostic IDs is capped at65536 accepted IDs for the process, no reuse/pruning; fail before ordinary effects at exhaustion. Safe-integer interaction revision must reserve two increments before ordinary operation acceptance (PENDING and terminal); no wrap. Stop must still initiate actual cleanup when revision/ID space is exhausted; preserve last representable revision, expose only fixed failure/unknown response, never invent a successful mutable snapshot or UUID. No result promises or cleanup work are dropped because logging/state representation cannot allocate.
