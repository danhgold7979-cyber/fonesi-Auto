## 2. Two explicit modes, no implicit historical continuity

- **CURRENT:** candidate is a unique native DEVICE row bound to an existing PROVISIONAL registry record. The transaction captures that exact deviceId; it cannot silently choose another record.
- **HISTORICAL:** candidate is a unique native DEVICE row whose claim is IDENTITY_REQUIRED with null deviceId after restart/reconnect. Caller also explicitly chooses an existing DISCONNECTED historical deviceId with no active binding. A retained historical VERIFIED marker after disconnect is not current authority; startup reconstructs PROVISIONAL. Both require this same fresh association. The operator separately attests “same physical handset as this record.” Choosing the record alone is not evidence. Refuse an already-live destination or another current claimant; never merge two histories or delete a provisional record to make the request pass.

Both modes run the full physical association; historical hashes/evidence never skip it. CURRENT is not allowed to infer a historical destination by matching serial. HISTORICAL is not an automatic resume policy. All other native normalized rows must remain unchanged, allowing a second handset to be enrolled without deliberately disconnecting the first.
